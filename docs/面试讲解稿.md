### 4. 目前的技术亮点

- JWT + 拦截器 + `ThreadLocal`，实现管理端/用户端鉴权。
- `@Transactional` 覆盖下单、改菜品、改套餐等核心写操作。
- AOP 自动填充创建/修改人和时间，减少重复代码。
- Redis 已用于菜品列表、套餐列表、营业状态缓存。

- `@Scheduled` 用于超时订单处理。

## 二、10 分钟项目介绍大纲

### 1. 项目背景（1 分钟）

- 这是一个外卖订餐系统，分管理端和用户端。
- 目标不是只做“能下单”，而是把“菜品展示、购物车、下单、支付、接单、催单”串成完整链路。
- 你可以说：`这个项目最开始是课程版单体系统，我在理解业务链路后，重点把鉴权、缓存、定时任务和消息提醒这些基础能力串起来。`

### 2. 技术架构（1.5 分钟）

- 后端是 Spring Boot + MyBatis + MySQL。
- 登录态用 JWT，用户身份通过拦截器解析后放到 `ThreadLocal`。
- Redis 用在营业状态和菜单缓存。
- WebSocket 用于实时提醒。
- 定时任务补足“没人点按钮时的自动处理”。
- 你可以说：`这套架构是典型单体架构，但我尽量把高频读、异步提醒、超时兜底这些能力前置。`

### 3. 核心功能（2 分钟）

- 管理端：员工、分类、菜品、套餐、订单、营业状态。
- 用户端：微信登录、浏览菜单、购物车、地址簿、下单、支付、历史订单、催单。
- 你可以说：`业务上最核心的不是页面，而是订单链路：登录、选餐、下单、支付、接单、配送、完成。`

### 4. 我负责的模块（2 分钟）

- JWT 鉴权和上下文传递。
- Redis 菜单/套餐缓存。
- AOP 自动填充。
- 订单超时处理和来单提醒。
- 你可以说：`我主要做的是把“功能能跑”升级成“请求链路更完整、读写更轻、提示更及时”。`

### 5. 遇到的挑战和解决方案（2 分钟）

- 挑战 1：登录后各层都要知道当前用户是谁。  
  方案：拦截器解析 JWT，把用户 id 放进 `ThreadLocal`，业务层直接取。

- 挑战 2：菜品查询频繁，数据库压力大。  
  方案：用户端菜品/套餐列表走缓存，管理端改动后主动失效缓存。

- 挑战 3：超时订单没人处理。  
  方案：定时任务每分钟扫一次未支付订单，超过 15 分钟自动取消。

- 你可以说：`我做的不是单点功能，而是围绕订单链路补基础设施。`

### 6. 收获（1.5 分钟）

- 理解了单体项目的分层方式。
- 明白了“能跑”和“能扛并发”差在哪。
- 体会到缓存、鉴权、异常、任务、消息提醒这些基础能力，决定了系统体验和稳定性。
- 你可以说：`这个项目让我从只会写接口，变成会思考高频读、状态同步和异常兜底。`

## 三、常见面试问题

### 1. 你这个项目怎么做鉴权？

参考答：登录成功后生成 JWT，把员工 id 或用户 id 放进 token。请求进来先经过拦截器，解析 token，取出 id 放到 `ThreadLocal`，后面的 Service 就能直接拿当前登录人。这样不用每层都传参，也不用服务器保存 session，适合前后端分离。

### 2. 为什么用 `ThreadLocal` 存用户信息？

参考答：因为一次请求只会在一个线程里处理，拦截器把用户 id 放进去，后续方法都能直接取。这样代码更干净，不用层层传 `userId`。但请求结束后要清理，避免线程复用时串数据。

### 3. 你们怎么做缓存？为什么用 Redis？

参考答：菜品列表、套餐列表、营业状态都放进了 Redis。因为这些数据是“读多写少”，直接查数据库会有很多重复查询。Redis 读写快，适合扛高频访问。当前项目里，用户端查菜品先读缓存，管理端改数据后再把缓存失效。

### 4. 缓存一致性怎么保证？

参考答：当前主要用缓存失效策略，也就是先改数据库，再删缓存，下一次读的时候重新查库回填。这种方式简单、实用，适合大多数业务。要更稳，可以加 TTL、延迟双删，或者用消息/CDC 做最终一致性。

### 5. 你这个项目怎么防超卖？

参考答：**当前仓库里还没有真正的库存字段和扣减逻辑，所以防超卖是“规划中”，不是已实现。**  
如果要做，我会先在数据库加库存字段，再用 Redis + Lua 做原子预扣，保证高并发下不会超卖；落库时再配合乐观锁，防止并发写冲突。为什么先用 Redis？因为它能把大部分请求挡在数据库外面，数据库只处理最终落库，压力小很多。

### 6. 为什么不用数据库直接扣库存？

参考答：数据库可以做，但高并发下会有锁竞争，性能和稳定性都不理想。Redis 可以先原子扣减，速度快、并发高，再由数据库做最终一致性校验。简单说，Redis 负责“先挡住”，数据库负责“最后确认”。

### 7. 全局异常处理是怎么做的？

参考答：项目里用 `@RestControllerAdvice` 统一拦截业务异常和数据库异常。业务异常直接返回友好提示，像重复用户名这种 SQL 错误会翻译成“用户名已存在”。好处是前端不用猜错误类型，接口返回也统一。

### 8. AOP 自动填充解决了什么问题？

参考答：新增和修改时，创建时间、修改时间、创建人、修改人这些字段每个接口都写一遍很烦，也容易漏。AOP 统一拦截 Mapper 方法，通过反射自动填充，避免重复代码，保证字段一致。它本质上是把“公共规则”从业务代码里抽出来。

### 9. WebSocket 来单提醒怎么做的？

参考答：客户端连接 `/ws/{sid}` 建立 WebSocket 通道，服务端保存 Session。用户支付成功或催单后，后端主动推消息给前端管理端。为什么不用轮询？因为轮询会浪费请求，WebSocket 更适合实时提醒。

### 10. 定时任务在这个项目里做什么？

参考答：一个任务是每分钟扫描超过 15 分钟未支付的订单，自动取消；另一个是每天凌晨处理长时间派送中的订单。这个设计的意义是补足“没人操作时的兜底”，避免订单卡死。

### 11. 你们分页是怎么做的？

参考答：用 PageHelper，在查询前先 `startPage`，它会帮我们自动拼 `limit` 和统计总数。这样不用一次把全表数据查出来，性能更好。订单详情这块目前有 N+1 的倾向，后面可以再做批量优化。

### 12. 下单流程里最关键的是什么？

参考答：最关键的是事务。下单时要先校验地址和购物车，再插入订单和订单明细，最后清空购物车，必须放在一个事务里，任何一步失败都要回滚。这样才能保证“订单、明细、购物车”三者状态一致。

## 四、项目亮点话术（STAR，规划中）

### 1. 下单防超卖（规划中）

- S：高峰期同时下单，数据库直接扣库存容易被打爆。
- T：既要防止超卖，又要保证下单响应快。
- A：规划用 Redis + Lua 做原子预扣，数据库用乐观锁兜底，订单成功后再落库；如果支付超时，再由定时任务回补库存。
- R：把压力前移到 Redis，数据库只做最终确认，系统更稳。

### 2. 缓存一致性（规划中）

- S：菜品和套餐查询频繁，改动后又怕脏数据。
- T：既要快，又要尽量保证读到的新鲜数据。
- A：规划采用 Cache Aside：读时先查缓存，写时先更新数据库再删除缓存；必要时加 TTL 和延迟双删。
- R：减少数据库压力，同时把缓存脏读窗口控制在可接受范围内。
