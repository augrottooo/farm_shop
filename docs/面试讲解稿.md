# 助农农产品电商平台面试讲解稿

> 本文只描述当前源码已经存在的能力。Redis + Lua 库存闭环已经落地；RocketMQ、Caffeine、优惠券、完整退款、快递物流和溯源不属于当前实现。

## 一、项目现状

这是一个从苍穹外卖演进而来的助农农产品电商平台，后端采用 Spring Boot + MyBatis + MySQL + Redis + JWT，使用单体多模块 Maven 工程。

当前商品模型已经完成替换：

- 商品主表是 `product`。
- 规格和价格、库存放在 `product_sku`。
- 购物车和订单明细使用 `product_id + sku_id`，不再依赖旧的 `dish_id`、`setmeal_id`。
- `stock_log` 记录库存初始化、订单扣减和订单取消/超时回补。

当前主要链路是：用户登录 -> 浏览商品和 SKU -> 加入购物车 -> 提交订单 -> 库存预扣和数据库扣减 -> 支付/支付回调 -> 商家处理订单 -> 用户取消或订单超时后回补库存。

需要主动说明的边界是：订单状态仍沿用原外卖项目的待接单、派送中等状态，支付入口目前是简化实现，快递发货、签收、优惠券、完整退款记录和溯源功能尚未完成。

## 二、10 分钟项目介绍大纲

### 1. 项目背景，约 1 分钟

**要点**

- 项目定位从餐饮外卖调整为助农农产品销售。
- 用户购买的不是无库存菜品，而是有规格、有价格、有库存的农产品 SKU。
- 目标是让系统从“功能可用”逐步具备“并发下库存不超卖、取消能回补、数据可追踪”的基础能力。

**参考话术**

> 这是一个助农农产品电商平台，项目是在原苍穹外卖单体系统的基础上改造而来。原系统的商品是菜品和套餐，缺少库存模型；我把它调整成商品主表加 SKU 表，并围绕下单链路补充了 Redis Lua 预扣、MySQL 条件扣减、库存流水和取消回补。当前项目重点是把商品、购物车、订单、库存这条主链路跑通。

### 2. 技术架构，约 1 分钟

**要点**

- `sky-common` 放通用异常、JWT 工具、上下文和公共结果。
- `sky-pojo` 放 DTO、Entity、VO。
- `sky-server` 放 Controller、Service、Mapper、配置、拦截器、定时任务和 WebSocket。
- MySQL 保存业务最终数据，Redis 承担高频状态和库存预扣。

**参考话术**

> 项目采用单体多模块分层架构。请求先经过 JWT 拦截器，再进入 Controller、Service 和 Mapper。MySQL 是最终数据源，Redis 用于店铺状态和 SKU 库存的高并发预扣，Lua 保证库存判断和扣减是一个原子操作。项目没有引入消息队列和 Caffeine，当前先把单体系统里的数据一致性闭环做好。

### 3. 核心功能，约 1.5 分钟

**用户端**

- 微信登录。
- 分类、商品和 SKU 浏览。
- 购物车和地址簿。
- 提交订单、订单查询、支付入口、取消、再来一单、催单。

**管理端**

- 员工登录和权限拦截。
- 分类、商品、SKU 库存管理。
- 订单查询、接单、拒单、取消、派送、完成。
- 店铺营业状态和 OSS 图片上传。

**参考话术**

> 用户端和管理端共享订单主链路。用户在商品详情选择具体 SKU 后加入购物车，下单时服务端重新读取 SKU 价格和商品状态，不信任客户端金额；订单创建成功后写入订单明细并清空购物车。管理端可以处理订单，也可以直接设置 SKU 的绝对库存。

### 4. 我重点完成的模块，约 2 分钟

**商品模型**

- 用 `product` 表表达商品，用 `product_sku` 表表达规格、价格、库存。
- `ProductDTO` 将商品和 SKU 一起提交，便于管理端一次保存。
- 用户端先查商品，再根据商品 id 查询 SKU 列表。

**库存模块**

- `StockServiceImpl` 初始化时把上架 SKU 库存预热到 Redis。
- Redis key 为 `stock:sku:{skuId}`。
- `resources/lua/deductStock.lua` 原子判断并扣减 Redis 库存。
- MySQL 使用带 `stock >= count` 条件的更新兜底。
- `stock_log` 记录库存变化前后值。

**订单模块**

- `OrderServiceImpl.submitOrder` 负责地址、购物车、商品和 SKU 校验。
- 订单先插入拿到 `orderId`，随后扣减数据库库存并写订单明细。
- 用户取消、管理端取消/拒单、超时订单会按订单明细回补库存。

### 5. 挑战和解决方案，约 2.5 分钟

#### 挑战一：高并发下如何避免超卖

**参考话术**

> 如果每个请求都先查 MySQL 再扣库存，高并发下会产生大量数据库竞争，而且“查询”和“扣减”不是一个原子动作。当前实现先用 Redis Lua 把读取、判断、扣减合成一个原子操作；Redis 失败时降级到数据库，数据库再用 `stock >= count` 的条件更新兜底。这样 Redis 负责快速挡住大部分并发，MySQL 负责最终确认。

#### 挑战二：Redis 扣了但订单失败怎么办

**参考话术**

> 下单过程中会记录本次订单已经在 Redis 预扣成功的 SKU。如果后续商品校验、订单插入、数据库扣减或订单明细写入失败，就对已预扣的 SKU 执行 `INCRBY` 回补；MySQL 事务则回滚订单和已经成功的数据库更新。需要注意 Redis 和 MySQL 不是同一个事务，所以额外做补偿，并记录补偿失败日志。

#### 挑战三：取消和超时后如何闭环

**参考话术**

> 取消订单不是只更新订单状态，而是先根据订单明细找到 SKU 和数量，回补 MySQL，再把 Redis 同步到数据库库存，并写一条 `RESTORE` 流水。定时任务每分钟查询超过 15 分钟仍是待付款的订单，调用同一个超时取消方法，避免用户不操作时库存一直被占用。

### 6. 收获，约 1 分钟

**参考话术**

> 这个项目让我理解了商品、SKU、购物车、订单和库存之间的关系，也让我意识到“能下单”和“并发下单不出错”是两个层次。现在的实现还不是完整生产电商系统，但已经把库存扣减、事务回滚、取消回补和流水审计这些基础闭环建立起来。后续如果继续演进，我会优先完善支付幂等、退款记录、快递履约和订单状态机。

## 三、常见面试问题

### 1. 为什么用 Redis + Lua，而不是直接查数据库扣库存？

**参考答案：**

直接查库再更新有两个问题：一是高并发时数据库会承受大量相同查询和更新；二是“查到库存”和“扣库存”之间可能被其他请求插入。Redis Lua 把读取、判断、扣减放进一次原子脚本执行，能快速挡住超卖请求。MySQL 仍然保留 `stock >= count` 条件更新，作为最终落库校验。

### 2. Redis 预扣成功，但 MySQL 扣减失败怎么办？

**参考答案：**

下单流程会保存已经预扣成功的 SKU 列表。只要后续任一步失败，就调用 Redis `INCRBY` 把这些库存补回；MySQL 事务则回滚订单和已经成功的数据库更新。需要注意 Redis 和 MySQL 不是同一个事务，所以 Redis 补偿失败不能假装成功，当前代码会记录日志，后续可以增加补偿任务。

### 3. 为什么数据库更新要写 `WHERE stock >= #{count}`？

**参考答案：**

因为它把“库存足够”变成了数据库更新条件。多个请求同时扣库存时，只有满足条件的请求能成功更新，返回影响行数为 `0` 就说明库存不足或 SKU 不存在。这样不依赖先查出来的旧库存，也能避免库存被扣成负数。

### 4. 为什么订单先插入，再扣库存？

**参考答案：**

订单先插入可以先拿到 `orderId`，库存流水的 `biz_id` 就能关联具体订单。订单插入、数据库扣库存、库存流水、订单明细和购物车清空都在同一个 Spring 事务中，任一步抛异常，数据库操作整体回滚。Redis 预扣则通过异常补偿恢复。

### 5. `stock_log` 记录什么？为什么要记录？

**参考答案：**

当前流水记录 `sku_id`、`business_type`、`biz_id`、`change_count`、`before_stock`、`after_stock`、备注和创建时间。`business_type` 的 `1/2/3` 分别表示初始化、扣减、回补。它的价值是出现库存对不上时，可以按 SKU 和订单追查每次变动，而不是只看当前库存。

### 6. 取消订单为什么要回补库存？

**参考答案：**

下单时库存已经被扣减，如果取消只改订单状态，商品会出现“订单没了但库存也没了”。当前取消流程通过订单明细逐个 SKU 回补 MySQL，再同步 Redis，并写 `RESTORE` 流水。超时未支付也走同一套方法，避免库存长期被占用。

### 7. Redis 不可用时系统怎么办？

**参考答案：**

当前下单逻辑对 Redis 异常做了降级：Redis 预扣失败时转为直接走 MySQL 条件扣减。这样可用性更好，但高并发性能会下降，数据库压力会上升。面试时应说明这是当前阶段的降级策略，生产环境还需要监控、限流和库存补偿机制。

### 8. 为什么启动时要把库存预热到 Redis？

**参考答案：**

Lua 脚本对不存在的 key 会按 `0` 处理。如果不预热，第一次下单可能被误判为库存不足。当前 `StockServiceImpl.init()` 查询上架 SKU，把数据库库存写入 `stock:sku:{skuId}`，保证 Redis 有初始值。Redis 预热失败时仍允许后续走数据库降级。

### 9. JWT 和 ThreadLocal 在项目中分别解决什么问题？

**参考答案：**

JWT 解决前后端分离场景下的身份传递，登录后把用户 id 或员工 id 放入 token，请求由拦截器解析。ThreadLocal 解决同一次请求中业务层获取当前登录人的问题，Service 不需要每层显式传用户 id。ThreadLocal 依赖线程复用，因此规范做法是请求结束清理，不能把它当成跨请求存储。

### 10. 支付入口现在是真实微信支付吗？

**参考答案：**

项目保留了微信支付工具和 `/notify/paySuccess` 回调接口，回调代码会读取通知、解密资源、按商户订单号更新订单支付状态，并返回微信要求的成功响应。但当前 `OrderServiceImpl.payment` 中真实统一下单调用被注释，使用了简化返回并直接更新订单状态，因此不能把它描述成完整生产支付闭环。后续需要补齐统一下单返回参数、签名验签、回调幂等和主动查单。

### 11. WebSocket 和定时任务分别解决什么问题？

**参考答案：**

WebSocket 用于支付成功后的来单提醒和用户催单，服务端可以主动推送，不需要前端频繁轮询。定时任务用于处理无人操作的场景，当前每分钟扫描超过 15 分钟的待付款订单并取消，同时回补库存。

### 12. 当前有哪些能力还没有实现？

**参考答案：**

当前没有 Caffeine、Redisson、RocketMQ、秒杀活动和多级缓存；优惠券表、退款记录表和物流表没有形成完整业务接口；溯源、农户档案、SaaS 多租户、微信订阅消息和区块链存证明确不在范围内。订单状态也仍是原外卖状态，快递发货和签收还需要后续改造。

## 四、项目亮点话术

### 亮点一：Redis + Lua 和 MySQL 条件更新防止超卖

**S - 情景**

商品从无库存的餐饮模型切换成了有 SKU 库存的农产品模型，下单并发上升后，直接查库扣减容易出现库存竞争和超卖风险。

**T - 任务**

在不引入消息队列的前提下，保证当前单体系统能够快速拒绝库存不足请求，并让 MySQL 保留最终校验能力。

**A - 行动**

在 `StockServiceImpl` 中使用 `StringRedisTemplate` 执行 `deductStock.lua`，将库存判断和扣减放到 Redis 原子脚本中。订单落库时再执行 MySQL 条件更新 `stock = stock - count AND stock >= count`。Redis 预扣成功但后续失败时，按已记录的 SKU 数量执行补偿；数据库扣减成功后写 `DEDUCT` 流水。

**R - 结果**

当前已经形成“Redis 快速预扣、MySQL 条件兜底、失败补偿、流水可追踪”的库存链路，能够在面试中清楚解释从功能可用到并发安全的演进过程。

### 亮点二：取消和超时订单的库存回补闭环

**S - 情景**

库存扣减后，用户可能主动取消订单，或者订单超过 15 分钟仍未支付。如果只更新订单状态，库存会被永久占用。

**T - 任务**

让用户取消、管理端取消/拒单、超时取消都能恢复对应 SKU 库存，并留下可核对的业务记录。

**A - 行动**

抽取 `StockService.restoreStockByOrderId`，根据订单明细逐个回补 SKU。回补 MySQL 后同步 Redis，并写入 `RESTORE` 流水；`OrderTask` 每分钟扫描待付款超时订单，统一调用 `cancelTimeoutOrder`。

**R - 结果**

订单状态和库存状态形成了基本闭环，库存变化可以通过 `stock_log` 追踪。当前还需要继续完善回补幂等，避免重复取消或重复回补造成库存膨胀。

## 五、一分钟电梯版

这是一个从苍穹外卖改造而来的助农农产品电商平台，技术栈是 Spring Boot、MyBatis、MySQL、Redis、JWT 和 Redis Lua。商品模型从菜品/套餐改成了商品主表加 SKU 表，SKU 保存规格、价格和库存；用户可以登录、浏览商品、加购物车和下单，管理端可以维护商品、SKU 库存和订单。我重点完成了 Redis Lua 原子预扣、MySQL 条件扣减、库存流水，以及取消和超时订单的 Redis/MySQL 双回补，让系统从“能下单”进一步具备“高并发下不容易超卖、失败后能恢复库存”的基础能力。当前支付仍是简化链路，优惠券、完整退款和快递履约属于后续范围。
